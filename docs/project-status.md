## 本批：码表与字体入库、去掉 JSON 数据包（2026-10-26，未部署）

- 来源：用户指出码表、字体被 `.gitignore` 排除，换电脑后无法重新打包，要求把需要的资源入库；码表不用 JSON（可读性差、加载慢）。
- 入库：码表 9 项原文放 `resources/tiger`（来源：虎码官网盘 <https://huma.ysepan.com/> 下载的“虎码秃版 小狼毫（Win）”方案包，码表版本 2026.08.14，未作修改），三个字体放 `resources/fonts`，Inno 简体中文语言文件放 `installer/ChineseSimplified.isl`，共约 57MB（Git 压缩后约 28MB）。`.gitattributes` 对三者设 `-text`：`tiger.dict.yaml` 与 `tigress_ci.dict.yaml` 为 CRLF/LF 混用，原 `* text=auto eol=lf` 会在入库时改写字节，本机工作区仍正确、换机检出后 SHA256 才不符。`tiger.lock.json` 删去不再使用的 57 项（Rime 配置、Lua、其余 OpenCC 文件）并加来源。原 `vendor/tiger`（已逐字节核对与只读原件一致）、`vendor/fonts`、`vendor/inno` 已删除；`vendor/` 只剩退役路线的 librime/essay/prelude 下载，仍不入库。
- 去掉数据包：删除 `import-resources`、`verify-package` 与 JSON 数据包（版本、摘要、保存/加载）；后台、`lookup`/`demo-input` 与打包驱动都直接读码表目录，按编译进程序的清单逐个核对大小/SHA256 后只解析所需数据段，缺文件时报错带路径。安装版码表在 `C:\Program Files\TigerType\tiger\`，安装时删除旧 `tiger-v1.json`。引擎词表类型不再序列化，engine 去掉 serde 依赖，架构规则同步收紧。
- 顺带修复：`.cache/tiger-v1.json` 是 v1 旧包，README 开发命令用它会被拒——已删除，命令改用 `resources\tiger`；`tiger-v1.json` 文件名与包内 v2 格式对不上——随数据包一并去掉。
- 测试：治理测试新增“锁定资源须已入库且为 `-text`”（反例：未跟踪、仍按 `text=auto` 规范化、同前缀的其他路径）与“engine 依赖 serde 即拒绝”；打包脚本测试改为逐个核对码表行与目标目录（反例：删去一行码表、把 opencc 子目录装平）；完整码表验收改为直接加载 `resources/tiger` 并记录加载耗时。
- 实测：从索引模拟全新检出（本机系统级 `core.autocrlf=true`），13 个锁定文件 SHA256 全部与清单一致。release 版 `lookup` 冷启动（加载+一次查询）约 0.63s，旧 JSON 包约 0.80s，两者输出逐字节相同；剖析为读取+SHA256 约 30ms、文本解析约 190ms、建词表索引约 200–240ms（与数据格式无关）。安装包由 17.5MB 增至 24.0MB。

## 本批：候选窗弹出滞后（2026-10-26，已安装本机）

- 现象：用户反馈 10-24 的 `UpdateWindow` 修复后候选窗仍常常“字打完了框还没出来”。那次修的一帧空框不是主因。
- 取证（临时诊断构建，只记事件标签与 QPC 时刻、不记按键内容，定位后已删除）：记事本首键到候选窗显示 5–11ms，后台与绘制都不慢。Chromium 系宿主（实测 Typora，另在 Claude 桌面应用误触一轮）的组合矩形由渲染进程异步回报：组合开始或改动后的同一编辑会话里 `GetTextExt` 时而返回 `TS_E_NOLAYOUT`（`0x80040206`），时而返回点击前的旧光标位置；Chromium 无系统光标可退回。旧代码此时直接隐藏候选窗——首键不显示、组合中途某键拿不到布局就收起，要等后面某个键恰好拿到位置才重新出现，短码已上屏时根本看不到。Chromium 随后 2–6ms 内两次发 `ITfTextLayoutSink` 布局通知带来真实矩形，但旧代码没有登记该 sink。
- 修复：编辑器在其上下文登记布局 sink（随编辑器释放注销），组合中且有候选时以只读会话（`TF_ES_READ | TF_ES_ASYNCDONTCARE`）核对自有组合后重取矩形，显示或移动候选窗；同一快照只移动、不递增展示编号、不作废待执行点击，位置不变不重绘。同小狼毫 `OnLayoutChange` 做法。
- 位置退路（同日第二步，应对既不给位置、也不发布局通知、又没有系统光标的宿主）：按键会话依次取整段组合矩形 → 组合起点（折叠范围）→ 系统光标 → 正在显示时的原位置 → 本输入框上次组合位置 → 输入区域（视图屏幕范围，取不到则视图/焦点窗口）；全零矩形视为宿主不知道。输入区域作为整体矩形交给原摆放规则，候选窗贴其外沿、不盖输入区。至此只要宿主有任一窗口，首键必出框；末两级只是近似位置，宿主补来布局即移到真实位置。
- 测试：新增 `layout_notices_reread_the_own_composition_read_only_and_stop_when_dropped`（只读标志、组合被改写不定位、无组合不定位、释放后不再通知）与 `late_host_layout_shows_candidates_and_a_missing_layout_keeps_them_in_place`（首键无布局不显示→通知后显示；中途无布局原位刷新；通知只移动、编号不变、仍可点选；未组合时通知不显示）。合成上下文增加 `ITfSource`。反例：去掉原位保持、不登记布局通知、同快照也递增编号，新服务测试分别失败，已恢复。退路另增 `missing_composition_layout_falls_back_to_the_insertion_point_and_reports_recent_and_area`（插入点、全零矩形、上次位置与输入区域随报告带出）与 `without_any_host_position_candidates_use_the_last_composition_then_the_input_area`（上次组合位置优先于输入区域、新输入框贴输入区域、无区域时用真实隐藏窗口作视图窗口）；合成视图可设插入点布局、全零回答、屏幕范围与视图窗口。反例：分别去掉组合起点、全零过滤、上次位置、输入区域、视图窗口五级，对应测试均失败，已恢复。
- 实测（安装版，无诊断）：Typora 每个组合首键 2–5ms 内显示，随后布局通知移到真实位置；Notepad++ 首键 9ms 内显示。诊断期间另见：刚启动的 Typora 点一下立刻打字时，第一个组合在 TIP 编辑会话返回后宿主自身阻塞约 45–65ms，之后不再出现，不属 TIP 可控范围。

## 本批：UI 清晰度与候选刷新（2026-10-24，未部署）

- 根因定位：后台引擎与命名管道在合成 1,000 轮“进入组合→退格”压力下 P95 `317.8µs`、最大 `1.6059ms`，最坏 8,192 条同码短码桶 100 轮重建 `297.5819ms`（约 `2.98ms`/轮），均未达到 50ms 主动等待预算；候选窗刷新布局 1,000 次总计 `117.653ms`（每次 `117.653µs`）。引擎原先每个按键扫描整张排序表并重新维护去重树，现已把去重桶前移到加载阶段。实际空框来自候选窗只调用 `InvalidateRect`，DWM 先显示边框而 `WM_PAINT` 要等宿主回调返回，导致内容延后一帧。
- 修复：应用进程启动最早阶段动态解析并声明逐显示器 DPI（旧 Windows 10 缺少 API 时回退默认 DPI），避免查字/设置页被系统整窗位图缩放；候选窗创建时临时切换逐显示器 DPI 并恢复宿主线程上下文，避免宿主 DPI 设置把候选文字二次缩放；候选窗显示后立即 `UpdateWindow`，同一回调完成文字绘制。
- 新增 `backend_key_round_trip_pressure_stays_within_input_budget`、`large_code_bucket_rebuild_stays_bounded_under_pressure` 与 `popup_refresh_pressure_stays_within_input_budget` 压测，分别覆盖 IPC、最坏短码桶和候选窗刷新；固定阈值为 P95 ≤10ms、短码桶 100 轮 ≤1s、候选窗 1,000 次 ≤1s（兼容 x86 调试构建），均使用合成数据，不记录实际按键内容。

## 本批：外部审阅修复（2026-10-24，未部署）

逐项核对 Codex 审阅记录，八个代码问题均属实，已修复：

1. 选中文字后输入吞键：预判吃下而编辑会话因非空选区拒绝，宿主未必交还原键。改为新组合（或直接提交）替换选区，同系统输入法；后台无结论时尚未写入，原键交宿主自行替换；取消只删组合、不恢复选区。只读上下文改在预判时用 `GetStatus`（无需编辑锁）放行，会话内仍复验。方案已写明新语义。
2. 组合中后台断开：预判发现离线时先撤回仍一致的自有组合（同步取消，拿不到锁时排队一次）并收起候选，再放行原键。
3. 点击锁不解除：排队选字会话过期或失效时仍以失败报告调用结束通知；受理结果同时检查内层 HRESULT，被拒即由调用方解锁。
4. 托盘菜单展开时停不下后台：菜单模态循环期间由系统线程池等待唤起邮箱事件，有信号即投递 `CANCEL` 让 UI 线程 `EndMenu`，并重新置事件交回事件循环；唤起请求同样会收起菜单。
5. 越界翻页把高亮改回页首：页码不变时不动高亮。
6. 保存中关闭重开设置显示旧值：成功回复同步设置控件（在途期间控件禁用，没有草稿可丢）。
7. 连续顶屏时热重载不生效：组合中收到的设置由引擎暂存，在组合结束处（顶屏的旧字上屏后、新编码开始前，以及退格删空、清屏、上屏）换上，已显示的候选不重算。
8. 字体安装失败误删他人文件：只在本次新建成功而写入失败时删除，`create_new` 失败不删。

复审（Codex 第二轮）又确认三处遗漏，已补齐：

- 离线清理漏掉单击 Shift：Shift 按下不吃键、抬起预判只确认连接。按下与抬起预判改为共用同一离线清理（`Active::online`）。
- `GetStatus` 失败仍预判吃键而会话拒绝：读不到宿主状态与只读一样在预判时放行。
- 停机唤醒只覆盖托盘菜单：改为所有系统模态循环共用——查字/设置窗与托盘窗口在 `WM_ENTERMENULOOP`/`WM_ENTERSIZEMOVE` 时登记线程池等待，`WM_EXITMENULOOP`/`WM_EXITSIZEMOVE` 时阻塞注销；收到信号时重新置事件，仍在模态中才 `EndMenu` 并向该窗口发 `WM_CANCELMODE`（取消移动/缩放）。上下文按值传窗口句柄，不再依赖栈对象。
- 第三轮复审：文本框（EDIT）自带的右键菜单不发 `WM_ENTERMENULOOP`（Codex 探针 `artifacts/review-edit-menu-probe.log`），停止仍会等用户关菜单。文本框子类过程在交给原过程处理 `WM_CONTEXTMENU` 前后自行登记/注销等待，并处理 `UNBLOCK`；登记改为返回是否由本次登记，嵌套时只注销自己的等待。
- 文档：README 导入文本数改为 9 项；方案中图标描述与热重载生效时机改为现行实现，并写明模态循环期间的停机处理。

复审新增测试：合成宿主可令 `GetStatus` 失败，预判放行；按键测试改为像宿主一样“预判不吃就不调处理回调”，离线测试分字母与单击 Shift 两条路径；查字窗弹出菜单（与系统菜单同经 `WM_ENTERMENULOOP`）与查询框自带右键菜单展开时停止后台，菜单须展开 200ms 以上（证明确实弹出）并在 3 秒内收起，事件循环随即退出。反例：Shift 抬起改回只确认连接、窗口过程不处理 `WM_ENTERMENULOOP`、或文本框不登记等待，对应测试均失败（后者菜单挂到 5 秒兜底定时器），已恢复。“至少展开 200ms”断言随即暴露旧测试的隐患：托盘与查字窗测试在不同线程同时弹真实菜单，后弹的会立即关掉先弹的（实测 33–39ms 即返回），此前这种情况被当作“已收起”而误判通过。弹真实菜单的测试现经同一把锁串行，且取得锁后才开始 300ms 计时，连跑 5 次均通过。第四轮复审指出耗时在回收停止线程（要等满 300ms）之后才取，菜单没展开也能过 200ms 断言；改为模态返回即取耗时，反例（文本框分支直接返回、不弹菜单）以 16µs 失败，已恢复。用户在测试期间点击桌面仍可能提前关掉菜单。

另删除旧 Win11Light 外观导入链路（数据包格式升 v2），README 去掉“Win11Light 外观”说法，本文删除 v3/v4 基线与已失效结论。

- 候选窗位置依赖宿主：Chromium 系宿主在布局通知到达前（实测 2–6ms）候选窗可能先在旧位置出现再移动；从不给位置、不发布局通知又无系统光标的宿主，候选窗退到上次组合位置或输入区域外沿，只是近似位置；连窗口都取不到时仍不显示。

- 安装包：提升权限的卸载 `stop` 可能被后台拒绝；从已提权进程启动安装包会拉起提权后台，所有宿主拒连，须以普通身份重启后台；升级时其他已登录用户的旧后台继续运行；安装中途失败时旧程序已改名，须重跑安装包。
- 本机 `C:\Windows\Fonts` 自带另一版 Cascadia Mono，与随包版本并存，由系统择一。
- 放开低完整性后同会话沙箱进程都能连接占槽，回收只能缓解拒绝服务；后台须以非提升权限运行。DLL 驻留为不可逆系统 PIN，不支持热卸载；管道关闭超时不等于资源已释放。
- 仓库含授权未确认的码表与字体，不得推送到公开远端；更换资源版本会使 Git 历史继续增大。后台每次启动全量核对并解析码表（release 约 0.45s），登录后首次输入前须完成；未测机械硬盘或低配机。
