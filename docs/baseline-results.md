## 实测环境与口径

- Windows 11 Pro，build 26100；AMD Ryzen 7 9700X，16 个逻辑处理器，系统可见内存约 63.6 GiB。
- Python 3.14.7；MSVC 工具目录版本 14.44.35207；7-Zip 26.03。
- 最终完整采样：`D:\Projects\TigerRime\artifacts\baseline-8l57sixk`。
- 环境记录：该目录的 `environment.json`；机器与字体注册表检查：`artifacts/machine-baseline.json`。
- 部署、测量各用一个限时子进程；每轮数据都来自新建的 `artifacts` 隔离目录，绝不使用 APPDATA。
- 所有进程统计包含 Python 工具自身、librime 和被加载模块。不是未来 Rust 管理 / 引擎进程的占用，更不包含宿主 TSF 增量。
- 延迟起点：调用 `process_key` 前；终点：取得当前页和提交内容、复制字符串、释放 Rime 返回内存后。不含 IPC、TSF 和窗口绘制。
- 普通输入预热后测试 `u`、`uni`、`d`、`kry`，共 4,000 个逐键样本；不是随机真实用户工作负载。

这仅是短自检，**不替代两小时压力和八小时日常稳定性验收**。

部署峰值明显高于输入进程，证明部署必须独立测量，不能共用引擎的最低 256 MiB 限额。

## 已复现但未修复的问题

1. **原计算器中间态报错。** 输入 `=1+2` 的最终候选正确，但原脚本对未完成表达式直接调用 `load(...)()`，产生：
   ```text
   LuaTranslation::Next error(2): .../lua/calculator_translator.lua:400: attempt to call a nil value
   ```
   基线工具记录该错误并以退出码 **1** 结束。因此“20 个输出断言通过”不能写成“完整基线全绿”。原文件和 vendor 快照保持不变；后续 Lua 安全改造须同时处理语法中间态、危险能力、计算量和错误传播。
2. **旧程序对照缺失。** 两次进程检查均未发现运行中的 Weasel / Rime；没有启动它，也没有采样真实输入。旧程序版本、延迟和占用均记为“未测”，不是零，参考源码也不是已安装版本。
3. **字体还需实际枚举。** 注册表名称检查未匹配 `LXGW WenKai GB Screen`；其他原候选字体名称有匹配。这不是 DirectWrite 字体族枚举，不能直接认定字体缺失，后续原生界面须确认回退效果。
